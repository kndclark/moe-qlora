## 3. THE PATCH

**Diff scope.** `diff -u orig/ include/` (J/patch.diff) is exactly this and nothing else:
- one identical guarded shim block (`#ifndef FI_SM120_CTA_TMA_SHIM`) in each header, placed
  after the last #include;
- 13 call-site renames, `cde::cp_async_bulk_tensor_4d_global_to_shared` -> `fi_sm120::tma_load_4d_cta`.

The 4 TMA stores (`..._shared_to_global`, stp.cuh:445/476/885/915) are left alone, which is
correct because stores lower inline. orig/ is byte-identical to the source agent's extract.
No drive-by changes. One side effect: the old continuation-line indentation is now misaligned,
which is cosmetic.

**Semantic equivalence.** I compared the shim against libcu++'s own
`cuda::ptx::cp_async_bulk_tensor(space_cluster, space_global, ..., int32[4], uint64_t*)` at
bundled `__ptx/instructions/generated/cp_async_bulk_tensor.h:593`:
- The asm string is identical except `shared::cluster` becomes `shared::cta`.
- Constraints are the same: `r` dst, `l` map, 4 x `r`, `r` bar, `"memory"` clobber.
- The operands convert the same way: `__as_ptr_smem` is `static_cast<uint32_t>(__cvta_generic_to_shared(p))`
  (ptx_helper_functions.h:90-94), and the barrier goes through `barrier_native_handle`.
- The shim uses `asm volatile` where libcu++ uses plain `asm`. This is equivalent, because an
  asm statement with no outputs is implicitly volatile.
- Libcu++ already ships this exact `.shared::cta` 4D overload (`space_shared_t`, line 639, PTX ISA
  8.6). An upstream fix could call `cuda::ptx::cp_async_bulk_tensor(cuda::ptx::space_shared, ...)`
  with no inline asm at all.

The cta-vs-cluster equivalence for non-cluster launches follows from the PTX shared-window rules
(I did not re-fetch the docs). The empirical side is strong: patched outputs match Triton and fp64.

**Other patch claims.**
- The shim is not arch-guarded. It changes the load on every target the header compiles for.
  That is harmless for non-cluster launches, but the "sm_120 patch" label reads narrower than it is.
- JIT every start / no AOT: correct. None of the 96 AOT SSU modules in the image's
  flashinfer_jit_cache matches `..._si_i32_..._nt_1_cs_i32_na_i64_sm100`.

**Non-repeatability is real, not a tool artefact.** The g7a run and today's Triton run have
identical first-turn prompt_tokens on 158/158 items, the same provenance and tool_versions, and
temperature 0. Yet 128 items with *no* tool calls on either side still produce different final
text. For example, held_out-cp-0 diverges at character 142.

A likely mechanism, INFERRED: research_eval.py runs `--concurrency 16` by default (line 1438), so
batch composition varies from run to run. Under `auto`, the SSU kernel choice itself also
flips between simple (batch <=2) and vertical (batch >=3).

**What the c=1 row actually measures.** It does not exercise the patch:
- Auto picks simple when batch x 64 heads < 2 x 82 = 164, which means batch <= 2.
- So fi-cta at c=1 runs the same unpatched-path **simple** kernel as fi-simple. That explains why
  the two c=1 numbers match (33.39 vs 33.61).
- The patched vertical kernel runs only at batch >= 3: the startup warmup (where attempt 6
  crashed), c=16, and the concurrent eval.
- Labelling the column "fi-cta (patch, auto)" and crediting its c=1 +5 % to it is misleading.
  That +5 % is FlashInfer-simple versus Triton.

**Expected size of the c=1 gain.** The kernel-level eager saving is (924.4 - 156.4) us, about
0.77 ms per token. That predicts 31.86 -> 32.7 tok/s (**+2.5 %**, ARITHMETIC). The measured
+4.8 % p50 is in the right direction and plausible. "Small, not clearly real" is fair.

There is also a confound: the run order was fixed (Triton first). Triton's c=1 started from a
cold GPU (1,560 MHz, 48 C; bench-c1.json gpu_before) and has sd 2.44 against 0.34. That
depresses Triton's mean, so the +8 % mean overstates the gain more than the p50 does.

**Is "fi-simple -5 needs repeats" fair?** Partly. Paired per-item analysis against today's
Triton (hit_and_grounded, exact sign test):
